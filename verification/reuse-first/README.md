## 本轮交付

实际由独立 Codex 起草者读取源版本固定的 cc-sdd requirements/design/tasks 资源，并由非作者审查者读取 cc-sdd task review 或 Spec Kit analyze 资源，生成并审查同一个批量报价功能的规划包。N 为不额外加载框架资源的原生基线；S 为 cc-sdd 资源适配；C 为 cc-sdd 起草加 Spec Kit 审查。不是安装或调用它们的原生 CLI/工作流引擎，也不是又做了一轮框架介绍。

新增的是 [17 份上游原始文件及来源记录](../../experiments/reuse-first/provenance.json)（含许可证）、[25 行显式宿主绑定](../../experiments/reuse-first/host-bindings.md)、固定输入、实际运行工件与评估证据。没有新增生产控制器/选择器/状态机，也没有把试验文件放进发行包。

- S 将成功 JSON 的内部空白/字段顺序变成逐字节硬约束，超出了原始需求。初审与修订复核都漏检；[可执行反例](contract-counterexample.json)证明两个语义相同、均合法的单行成功输出会被该错误判据区别对待。未执行任何批量功能实现。
- S 初审的两个必改意见均未达到固定门槛：具体测试向量已能从整包交叉读取；方法说明已在合同指定的起草报告内，只是审查读取白名单漏给了这些文件。主线程当时接受 M1 导致一次不必要返工；不隐藏这一判断失误。M2 上下文修正也有完整记录。
- 因上述审查上下文修正与不对称返工，本轮不能宣称是无污染的严格对照；只能作为有限可行性与失败分析证据。不得由 N/C 通过或 S 失败推出框架普遍优劣。
- 三次负向检查仅证明新审查者在这个受控样例中识别并拒绝“旧接口改名＋必要测试可选化”；不是广泛安全或可靠性认证。
- S 的单次修订预算已耗尽，保持失败候选，不追加重试、改门槛或抹掉旧结果。

## 接入裁决

保留原生轻量基线，cc-sdd 规划资源与 Spec Kit 只读审查作为按阶段可选能力；不强制所有任务加载所有模板。保留单一规格/授权权威、独立审查、原版来源与显式路径/授权适配。拒绝在此接入上游自动批准、第二套状态目录或新的通用工作流引擎。BMAD 全量架构工作流本轮未运行，既有 Codex team 能力不因本次试片获得新的全流程验收。

下一步仍在同一计划内，先冻结小范围接入合同与失败用例：

1. 审查输入必须完整引用规格、宪法、工件、起草报告与消费证据，不能因读取白名单漏项而制造“缺失”；无需把同一说明复制到多处。
2. 验收既不能弱化规格，也不能擅自加严。本例成功响应比较 JSON 语义、键/数值、单行换行和退出行为；只有规范固定的错误行和旧兼容样例才逐字节比较。
3. 在这些失败用例固定后，再将上游阶段产物映射到既有治理/版本/任务/日志接口，明确哪些依赖因规格变更失效。当前 composite assessment 与 versioned-plan 接入仍未实现；先冻结确切接口和 RED，再分派必要代码。不要先写新调度引擎。

以上是基于本轮发现的接入方向，不是已经安装/上线的行为，也不是另一份进度账本或批准指纹。

## 验证与保留边界

[最终完整性检查](final-preservation.json)：52 冻结输入、201 保护文件且所查范围无新增、147 归档条目、28 负向副本文件、17 原始资源均通过；复制的现有三模块基线 6/6 断言通过。仅 S 的设计/任务草案发生获准修订，旧现场、历史审批及安装缓存的所查文件未变。

主线程校验首次失败也保留在 [attempt 1](preservation-attempt-1.json)：误将旧记录的 `.git/HEAD` 文件 SHA-256 当作提交号。只读核对确认原目录本来是未提交仓库；按历史文件哈希及索引缺失状态复查后通过，没有初始化、提交或改动旧现场。

模型配置为实际派发记录，不是自述证明：[dispatch record](dispatch-record.json)。起草/审查请求 default Sol/high，最终评估请求 default Sol/xhigh；接口只返回任务名，实际模型/effort、token、费用和隐藏上下文容量不可认证，均未臆造。起草工件初始体积 N 21,307 字节、S 33,784 字节、C 36,429 字节；S 修订后 37,374 字节。体积不是 token/成本/质量，时间也不能用于单次速度排名。
