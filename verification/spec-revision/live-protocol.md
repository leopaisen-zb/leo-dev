# Bounded source-loaded revision acceptance

Frozen before implementation/consumer runs. This is a controlled revalidation fixture, not an installed-client acceptance or general GPT-5.6 evaluation. Runtime P3 cases remain owned by the implementation brief; this adds actual independent review and entry consumption evidence, not different product requirements.

Fixture: two dependent tasks, A (name normalization module) → B (CLI wrapper). V1 trims leading/trailing whitespace, preserves internal characters and emits one CLI newline. V2 makes the already tested Unicode/internal-space behavior explicit and binds a small local constitution. The application is already compliant: revalidation should not force a code rewrite.

1. Main creates isolated correct application/test inputs and records source hashes. Public P1/P2 packaged CLI establishes a V1 dependent plan and real Gate/submission evidence. A separate actor reviews actual candidates; its judgments, not a predetermined pass, feed the existing review receipt seam. Approval envelopes used in this isolated exercise are labelled synthetic fixture grants, not genuine human/platform attestation.
2. Freeze V1 journal prefix, source/tests, Gate evidence and accepted receipts. Stage V2 documents/plan. Actual updated source/package must refuse the old authority and then activate the explicitly bound synthetic revision grant with ready assessment; retain the original prefix/bytes and reset A/B to revision 2 ready/pending. An unchanged application is permitted, not a reason to carry forward V1 pass evidence.
3. Actual development-entry consumer reads the new reference and current state. It must use the supported proposal/assessment/grant operation, recognize that current success needs fresh Gates/review, and preserve application/tests, task IDs and the fixed outcome. Its initial errors, missing context and corrections remain recorded; no repeated sampling to manufacture a clean result.
4. Run A and B's current-version Gates through the real CLI, with a genuinely separate reviewer for new candidate evidence. B cannot start before A's new review succeeds. Old review receipt must be rejected. All tasks reach current-version done only through fresh evidence; integration may then proceed.
5. Main records actual commands, source/runtime provenance, before/after hashes and final state. Independent source review and full regression remain separate evidence. Retain failed/intermediate results and distinguish simulated crash cases from actual interruption/context continuation.

Required outcomes: exact byte/history preservation; no unnecessary application rewrite; new Spec/constitution identity and all-task revisions; no old success/approval reuse; correct dependency sequence; actual independent candidate reviews; honest unsupported/partial classification. No new performance threshold, subprocess timing relaxation, source format restriction or hidden acceptance is added. No installation, Git, external service, or changes to the old C3/N/S/C fixtures.
