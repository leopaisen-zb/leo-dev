# Leo Dev 代码质量与验收差距评估

日期：2026-09-15。范围：当前 Codex/macOS 版本。主线程核对 Linux 官方资料、既有实测记录及过程验收；独立 Terra/high explorer `/root/quality_gap_audit` 只读核查代码与 CI。没有运行新测试、修改产品代码或配置。本报告是建议，不激活新的规格、验收阈值或发布权限。源码身份见 [source-snapshot.json](source-snapshot.json)。

## 对标含义

把 Linux 的工程要求应用到 Leo Dev：职责清晰、可审查的小改动、明确的状态和错误语义、兼容性、错误路径测试、维护者审查与回归处理。不能把一次测试通过或格式检查视为“达到 Linux 内核质量”的认证。TypeScript 项目应使用适合自身运行时的工具；不照搬 C 的缩进、引用计数或内核专用检测器。

Linux 官方来源（本轮实际读取）：

- [Coding style](https://docs.kernel.org/process/coding-style.html)：函数单一职责、可读性、错误清理路径和返回语义。
- [Submitting patches](https://docs.kernel.org/process/submitting-patches.html)：每个逻辑改动独立且可审查；优化主张需要测量；测试与审查分别提供证据。
- [Kernel Testing Guide](https://docs.kernel.org/dev-tools/testing-overview.html)：内部单元测试、公开接口系统测试、覆盖率、动态与静态分析互补，检查器不能替代判断。
- [Handling regressions](https://docs.kernel.org/process/handling-regressions.html)：用户可见的兼容性与回归处理。

## 独立代码核查的主要发现

没有确认可复现的运行缺陷。以下是维护性或验证覆盖差距，不应写成已发生的数据损坏或安全漏洞。

1. **控制器职责集中。** `packages/cli/src/controller/controller.ts:504` 所在文件有 3,181 行、81 个方法，包含 17 个命令入口，并集中处理分发、日志重放、治理、Gate、恢复、审查与归档。`batch.ts` 已抽出事务投影，但主要领域判断仍集中。长度本身不是缺陷；这些职责共同变化使跨状态审查困难。建议按现有领域边界逐步抽出独立决策模块，分离纯判断与 I/O，避免一次大重写或只为缩短文件而切碎函数。每一步用相同的公开行为与恢复检查验收。
2. **严格类型已有基础，事件解码仍有改进空间。** `tsconfig.base.json:6` 开启 strict，独立搜索在 CLI 源码中未发现 any。`state/types.ts:7` 的 payload 使用 unknown 是合理的输入边界；但 `controller.ts:123` 的 `latestPayload<T>` 在通用对象转换后承诺泛型 T，该文件有 51 处类型断言，动态分发也需要双重 cast。关键路径另有校验，不能据此宣称运行漏洞。建议外部/持久化数据先按事件类型验证解码，再进入带判别字段的类型联合；拒绝错误形状并接受合法历史数据。
3. **CI 有功能门槛，缺少持续的结构与覆盖反馈。** `.github/workflows/ci.yml:8` 在 macOS 15/Node 22 上执行 typecheck、主测试、doctor、示例与打包检查；根 scripts/CI 未配置 lint 或 coverage 采集。建议先取得关键分支覆盖和静态检查基线，再补具体盲区。不要从零规定一个全库覆盖率数字，也不把行数或警告数量当作质量结论。本轮继续聚焦当前 macOS，其他平台验证不自动扩大进度范围。
4. **故障与并发测试是现有强项，但覆盖模型有限。** recovery/fencing/Gate 测试已有残缺日志尾、CAS 冲突、过期 worker、进程重启、子孙进程约束，以及两路恢复只有一个后继执行等用例。controller batch 的显式 fault point 为 `after-batch-prepared` 与 `after-batch-projection`。尚不能据此断言任意进程终止、所有磁盘失败或交错均覆盖。建议列出实际持久化边界，按风险补独立进程终止与可控制的文件系统失败用例；不以大量随机运行替代明确的不变量。

## 结果校验：分别检查三种结果

| 对象 | 可判定的结果 | 合适的证据 |
| --- | --- | --- |
| Leo Dev 自身 | 正确命令被接受，错误/过期操作被拒绝；重试不会重复副作用；恢复保留合法工作 | 纯规则单测、公开 CLI 契约、状态序列与故障注入、安装包真实调用 |
| Leo Dev 开发出的代码 | 满足批准的行为、错误与边界契约，兼容既有用户行为，维护成本合理 | 独立行为验收、真实系统/浏览器检查、架构和代码审查；性能主张另测量 |
| 上游方法和 Agent 集成 | 实际使用选定方法完成任务，真实成员协作，交接、审查、修复可复现 | 安装后的真实 Codex 会话、宿主调用记录、任务工件及独立验收；仅资源存在或 HELP 成功不足 |

已记录的 0.2.0 开发演练确实通过过完整生命周期，并由审查发现原 Gate 未覆盖的未来时间导入/编辑/重启故障；这是有价值的单场景证据，不是所有任务可靠性的证明。原有 472 测试与最近 26 项相关测试属于各自版本和范围，本轮未重新执行。

代码审查应回答：这个复杂度是否必要；数据和副作用由谁拥有；错误后状态是否明确；旧接口是否兼容；资源如何释放；下一次改动是否能在局部推理。每项阻塞意见应引用契约、代码位置或可复现反例。没有依据的“更优雅”属于建议。

## 过程校验：约束关键事实，保留方法选择空间

1. **输入基准。** 记录批准的需求、任务和验收版本；新增事实可以促成显式修订，不能为使失败通过而私改标准。检查正确输出没有被擅自加严，错误输出没有被放行。
2. **实际分工。** 保存真实宿主返回的成员身份、所请求的模型/effort、任务范围和交接输入。宿主未提供有效模型确认时记未知。角色标签、共享 Markdown 或成员自述不能独立证明调用或身份。
3. **审查独立性与完整上下文。** 对需要独立审查的工作，审查者与实现者分离。审查者读取同一版规格、完整候选和必要报告；不提供预设结论。单独评价漏检和误报，不能以问题数量判断审查质量。
4. **执行与证据绑定。** 保存命令、退出状态、必要输出、候选版本和实际结果。CLI exit 0 可能仅表示“拒绝回执已记录”；完成判断必须看协议结果和当前任务状态。改代码后旧测试或审查不能自动沿用。
5. **失败与恢复。** 保留原始失败、未完成工作、修复次数和旧代次。检查过期消息被拒绝，同时新代次的合法结果能通过，避免用“全部拒绝”获得假安全。
6. **交付。** 在干净的消费环境中验证对应包/工件，独立区分通过、失败、未运行、阻塞和不适用。过程记录不用保存私人思维链，也不要求模型采用相同的推理方法或模板顺序。

已有复用试验曾因审查输入缺少指定报告而产生不必要返工，也曾对合法 JSON 输出擅自施加字节顺序要求；这些应成为审查过程本身的回归样例。见 [原始试验记录](../reuse-first/README.md)。

## 建议的验收节奏

行为改动先明确反例与结果契约，配合实现过程中的小步测试；任务完成时做独立规格/代码审查和公开行为校验；安装或发布候选做整体验证与关键故障回归。微小文档/元数据改动只用相称检查。把漏检、误报、实际人工干预、重复工作，以及可获得的耗时/成本作为 Leo Dev 自身版本改进记录；不要求每次和原生 Codex 对照。

对当前候选，已发现的数据丢失、旧证据被误接受、必要验收未跑却声称完成等严重问题应阻断交付。所有已执行样例通过，只能说明它们的结果；样本量、故障模型和未测环境必须保留。不以更多 Agent、更长文档或更高测试计数作为完成条件。
