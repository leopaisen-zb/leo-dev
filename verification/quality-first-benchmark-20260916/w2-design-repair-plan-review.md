# W2 candidate A design review

**Verdict: PASS — no material design blocker.** The proposed edge closes the observed same-change repair gap without granting new specification authority, reopening tasks, changing task revisions, or adding a command/state. The implementation may proceed after W1 closes, subject to the focused checks below.

## Why the design fits the current controller

- The observed gap is real. The current graph permits `design-review -> design-approved` but not a return to `spec-approved` (`packages/cli/src/state/transition.ts:4-6,29-32`). `requestDesignReview()` can capture revised design bytes only after the change is back in `spec-approved`, while `approveDesignReview()` is pass-only and requires the old immutable source to remain current (`packages/cli/src/changes/design-admission.ts:31-67`).
- A reject receipt already has the correct typed schema and exact binding fields: change, spec, normalized plan, design hash, producer session, verdict, findings, timestamps, provenance, and reviewer session. Reusing `receipt.design-review.ingested` preserves the original request and rejection append-only; `latestDesignReviewContext()` and `latestDesignReviewReceipt()` then naturally select the later request/pass pair without deleting history (`packages/cli/src/changes/design-events.ts:43-64`).
- Returning to `spec-approved` does not create or renew approval authority. `currentAuthority()` continues to derive the same initialized/revised specification authority, and the current transition projection can preserve the existing `approvalRef`/`approvalHash` in both manifest and spec artifacts. The rejection must remain a separate design-receipt operation and must never populate the specification approval projection.
- The existing controller batch is sufficient for atomicity. A prepared batch contains both logical operations and the manifest/spec projections; logical events become visible only beside the matching commit. Pending batches block ordinary commands, and `resume` reapplies only prior-or-desired projections before committing (`packages/cli/src/controller/batch.ts:224-259`; `packages/cli/src/state/snapshot.ts:95-141`). Thus the rejection event and back-edge cannot be partially accepted or ingested twice through ordinary recovery.
- Task records remain at their existing revisions/states while the Change returns through design review. Claims still require Change state `executing`, so retained ready tasks cannot execute during the repaired design cycle (`packages/cli/src/controller/controller.ts:2577-2586`). A rejected design receipt therefore cannot admit a claim or satisfy non-Lite `task-ready`.

## Required implementation checks

1. Add a distinct reject-admission result/guard. It must share the current context, authority, source-current, receipt-ID reuse, exact binding, provenance, independence, and temporal validation logic, but require `verdict === "reject"`. Do not overload `approvalReceiptMatches` or the existing pass-only result in a way that lets a rejection act as specification approval or design approval.
2. Permit the new edge only for exact `design-review -> spec-approved`. A reject receipt must fail from every other source state; a pass receipt must fail on this back-edge; Lite routes and missing receipts must remain read-only failures.
3. Keep operation order in one `transition` batch: `receipt.design-review.ingested` for the current rejection, then `change.transition`. Preserve the preexisting specification `approvalRef` and `approvalHash` exactly in both projections. Do not validate this back-edge as a fresh root/spec approval or replace those fields with the design receipt.
4. Validate the reviewed design before any edit: current repository bytes must still equal the immutable request hash when the rejection is prepared. After the committed rejection, a new `controller.design.review.requested` event must bind the repaired bytes and current producer session. Only a new unused, unexpired independent pass receipt for that latest context may reach `design-approved` and then `task-ready`.
5. Route execution and `--dry-run` through the same state-aware receipt acquisition. The current dry-run receipt-kind shortcut recognizes transition receipts only for `design-approved` (`packages/cli/src/controller/controller.ts:622-625`); extend it without misclassifying the ordinary `spec-review -> spec-approved` path or changing behavior merely because an irrelevant receipt argument was supplied.
6. Exercise both controller fault boundaries used by this batch path: after prepare and after projection. `resume` must yield exactly one rejection event, one back transition, matching preserved approval projections, and no partial or duplicate history. Invalid, expired, future, reused, mismatched, self-review, changed-design, and wrong-verdict cases must leave journal and projected files unchanged.
7. Retain the current lifecycle source of truth. The canonical table presently says unlisted transitions are forbidden, so the existing lifecycle documentation should record this guarded W2 edge and its reject-only condition. This is documentation of the authorized bounded repair, not a second specification tree or renewed application-spec approval.

## Evidence limits

This review establishes that the proposed controller shape is compatible with the current state, receipt, projection, and recovery mechanisms. It does not validate an implementation, installed package, or benchmark improvement. The existing local provenance strings remain unauthenticated metadata, as the plan already states; the new edge must not claim stronger reviewer identity guarantees.
