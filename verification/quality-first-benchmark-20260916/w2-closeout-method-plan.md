## Hypothesis and evidence limit

W1 showed that documents and green suites can miss public failure contracts.
The cc-sdd, Spec Kit and BMAD feature answers each retained a concrete defect;
some planning artifacts narrowed the original requirement. Leo caught these
boundaries in this case, so W1 does **not** establish a corresponding Leo product
defect or prove that another method will improve it. This treatment tests whether
explicit original-intent coverage and repair ownership are useful without
regressing already accepted behavior or introducing routine confirmation.

Compare A against A+B with the same installed runtime, native host, model,
permissions, budgets and two frozen DEV cases. Preserve both outcomes and check
actual resource consumption. A passing package test or a skill-name mention is
not evidence of behavioral benefit. Keep the final choice separate from the
experiment; do not claim causal superiority from one run per development case.

## Host binding

Use one existing requirements/design/tasks/constitution binding. Select the
packaged review and fresh-evidence resources for nontrivial task acceptance or
repair review. A sufficient existing review can supply the same evidence; do
not create duplicate reviewer sessions merely to attach another framework name.

As part of the last ordinary implementation task's independent review of its
**submitted candidate**, use the read-only intent-inventory and gap-classification
parts of Spec Kit convergence against
the **original approved intent**, actual implementation and relevant checks.
Preserve stable requirement identifiers. Cover each required behavior and its
stated failure conditions; green tests or coverage counts alone are insufficient.
Return verified, failed or unverified evidence, and concrete
`missing / partial / contradicts / unrequested` findings where applicable.
Do not invent failures, stricter serialization/algorithm choices, or unrequested
features. The model chooses suitable probes and implementation approaches.

Bind the review input and findings to the current change ID, task ID/revision,
Run ID, lease generation, specification/task hashes and submitted tree hash.
After any remediation, fresh claim, Gate and submission, repeat closeout on the
replacement submitted tree or explicitly re-evaluate every inventory item and
prior finding against that exact tree. A review of the preceding tree cannot
pass the replacement candidate. Use the existing candidate-bound review receipt;
do not introduce another receipt type or completion ledger.

Record findings in the existing review/verification channel. Do not create a
second editable completion ledger or mutate a frozen candidate to store a report.
The actual controller remains responsible for all states and receipts.

For a current submitted task, use its actual candidate-bound rejection and
remediation path; repair within its approved scope, then run fresh checks and
independent review. A still-live ordinary task may repair earlier files only if
its existing allowed paths and scope permit it. A done task cannot be reopened,
and the verification-only integration task cannot carry product edits. Otherwise
prepare the existing revision proposal and report the real authority boundary;
do not append tasks, fabricate approval, edit controller projections, or restart
the feature under a new change merely to avoid the boundary.

Disable upstream scripts/hooks, metadata/task-checkbox writes, automatic commits,
new artifact trees and completion-command engine dispatch. Adapt cc-sdd's
mandatory format/marker rules: verify actual applicable RED evidence without
requiring a specific field label; distinguish existing/justified comments from
unimplemented required behavior; follow project-specific checks and risk instead
of rejecting on a marker string. Keep original requirements authoritative and
classify evidence absence separately from a proved code defect.

Override the raw review's Git-first instruction: controller claim input, allowed
paths, candidate registration, submission binding and the controlled tree define
the review baseline. Inventory and read all relevant files, including untracked
files. Git diff is an auxiliary view only when its baseline is valid; an empty
diff or missing HEAD cannot prove that no implementation changed.

Use completion claim types `TASK` for task acceptance, `FIX` for repair, and
`TEST_OR_BUILD` for individual command claims. Do not select `FEATURE_GO` or
import its boot-smoke checklist/GO language as task, integration or release
authority. Keep project-specific verification and later release evidence
separate. Missing required environment evidence remains unverified or
`MANUAL_VERIFY_REQUIRED`, distinct from a reproduced product defect.

A separate Terra/high worker can own the selected raw resources, provenance,
`scripts/upstream-resources.mjs`, and necessary concise bindings in existing
develop references/entry. It must preserve candidate A's lifecycle correction
and change no controller, model routing, benchmark, threshold or held-out input.
Before images and exact package identity are required.

Before freezing B, retain the complete A-to-B package delta. Accepted A runtime
code must remain byte-identical; enumerate selected resources/licenses,
provenance/verifier entries, concise bindings and generated package metadata
separately. No unexplained runtime, controller, model or protocol delta belongs
in the method comparison.

Use the existing packaging/resource validation, skill validation and independent
review. Behavioral evidence comes from fresh A+B DEV actors: inspect whether
the source methods were actually read, whether original requirements and valid
alternatives survived, whether in-scope repairs continued, and whether the actor
invented extra approval or completion authority. Do not add text-presence tests
as proof of effectiveness. Held-out actors run only after the final candidate
selection and installed-package freeze.

Retain B only if both DEV products pass independent acceptance, necessary
methods are actually consumed/applied to the current candidate, and review does
not introduce unmet requirements, invented authority or unnecessary routine
confirmation. Otherwise keep the failed/unverified treatment visible and use
accepted A while resolving the demonstrated method defect separately. Even a
retained B supports only these bounded observations, not a causal performance
or general framework-ranking claim.
