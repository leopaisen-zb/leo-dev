# 框架、社区实践与 Codex 团队适配：第二轮深度调研

后续决定（2026-09-10）：用户已批准本报告提出的计划，并明确加入真实 Codex team 实现后授权开工。执行真源现为既有 spec v1.4.0 的 C3 修订及原计划 Active C3。本报告的研究时状态/结果保留为历史，不把建议改写为已实现；实施证据另见 `verification/codex-team/`。

## 1. 结论与范围

BMAD 的角色化协作可以适配 Codex；当前宿主已经具备实际子代理与后续消息能力，但这不等于 Leo Dev 已完成适配。推荐保留完整生命周期，目标工作流将选择性适配 BMAD 的生命周期/工程判断、cc-sdd 的完整 SDD、Spec Kit 的宪法/一致性/实现收敛、Superpowers 的工程方法。Codex 提供实际代理运行；Leo Dev 的目标职责是统一工件引用、完成准入、恢复与安装入口。不要同时引入几个相互竞争的总控。

这不是“再做一个简化编码循环”的提议，也不是整仓重写的决定。此前最主要的问题是：把用户的完整产品目标分割成底层任务，却缺少持续检查“组合后是否仍覆盖原始需求”的验收。局部完整性测试不能证明全流程完整。

研究问题：①这些框架真正实现了什么；②社区在组合/持续使用时踩过什么坑；③BMAD 团队如何接到 Codex；④怎样避免再次偏离用户要求。

研究边界：本地九个固定提交快照的相关源码、公开官方文档、公开 GitHub 原始问题与工程团队实践。主要关注 2026 年资料，2025 年案例标明历史背景。复用已有调研，并补读团队、平台接缝、版本变更与社区反例，不声称九仓全部逐行阅读。没有上游运行实验、插件安装、全产品测试或生产修改。

当前候选控制器在此前受控、source-loaded 的 C2 live 验收中未通过，详见 [已有真实失败记录](../../../verification/codex-execution/live-20260910/README.md)。这不等于已安装入口经过同样测试。本报告不修改 [规范规格](../../../.scratch/unified-development-plugin/spec.md)、审批或安装缓存。

## 2. BMAD 团队模式能不能改为 Codex 使用

### 2.1 必须分清三件事

| 对象 | 实际机制 | 对 Codex 的意义 |
|---|---|---|
| BMAD 生命周期 | hub 将需求、规格、架构、stories、build、retro 等技能连接；命名 persona 不是所有流程的必需品 | 可以复用阶段职责，不必让用户手动召集全部角色 |
| BMAD Party Mode | session 是单上下文模拟多角色；subagent 是真实代理分轮讨论；agent-team 的固定版本文档限定 Claude Code | 适配真实子代理和消息机制；不能把模拟讨论标成独立审查 |
| BMAD Build Auto / BMAD Loop | 前者是实现/审查技能协议；后者是独立运行器，已有 Codex profile | “BMAD 完全不支持 Codex”不成立；但已有 profile 不等于满足我们的权限和恢复要求 |

源码依据：BMAD `skills/bmad/references/help.md`、`skills/bmad-party-mode/{SKILL.md,references/mode-subagent.md,references/mode-agent-team.md}`；BMAD Loop `src/bmad_loop/data/profiles/codex.toml`。精确提交和定位见 [证据清单](sources.md)。这些是官方单源静态事实，不是本轮运行验证。“Claude Code only”是该模式文档的宿主限定，不是 Codex 无法通过实际消息能力实现逻辑持续团队的证明；跨会话存活、安装发现与工程恢复仍须验证。

Codex 官方说明支持专门子代理、跟进指令与结果汇总，并支持项目级自定义角色文件；本地 CLI 只读检查为 `0.153.4`，本会话实际提供 spawn/followup/message/wait 等能力。角色名称、实际线程和权限不是同一事物；官方配置能力也不能证明插件里的角色文件会自动加载。[官方 Subagents 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)

### 2.2 建议的适配接缝（未实现）

| BMAD 需求 | 建议的 Codex 适配 | 验收重点 |
|---|---|---|
| 项目团队和阶段选角 | 包内角色职责/阶段组合，绑定宿主实际代理；优先用受支持通用 agent 携带角色 brief | 每个关键职责有 owner；不是安装一堆独立入口 |
| 独立初始意见 | 清洁上下文分别派发架构与测试/领域审查 | 审查者不是实现者；保留真实返回，不伪造对话 |
| 交叉质疑与修订 | 先独立意见，再针对具体分歧跟进；支持点对点则使用，否则由协调者转发 | 不提前给审查者灌入“正确答案”；明确是否转发 |
| 持续角色身份 | 逻辑角色、宿主线程、工件版本分别记录；能复用则 followup，丢失则重建并明示 | 不承诺客户端退出后线程/进程常驻 |
| 团队意见形成决定 | 主协调者按证据和授权裁决，用户处理意图/权限/重大架构取舍 | 不用投票或“大家同意”替代依据 |
| 工程任务推进 | 完成状态仅由一个持久机制接受；讨论记录只作证据 | 无双重账本、迟到结果不能覆盖新版本 |

本会话有四个并发槽（含主线程），不是建议给所有 Codex 用户写死的限制。角色职责可以多于并发代理数；阶段间轮换或顺序运行仍是真实独立工作。是否需要站立式点对点团队，应由任务证明收益，而非把 Party 的所有角色常驻规则完整搬入开发。

对“团队适配可行”的判断是依据源码和当前宿主原语的工程推断（待验证），不是已通过适配测试。当前没有证明跨客户端、跨会话生命周期、安装角色发现与未知副作用恢复。客户端缺能力时应明示降级；要求独立审查的任务不能以单代理扮演替代。

### 2.3 为什么不直接运行 BMAD Loop

固定快照已经提供 Codex 配置，**不应再称 Codex 执行全无上游基础**。但 profile 含 `--dangerously-bypass-approvals-and-sandbox`，通用适配器在未配置 extra args 时采用它；初始化还会安装 hooks/relay/skills、改 policy/gitignore。它拥有自身 run state、journal、sprint 状态与 Git/worktree 生命周期。直接并列接入会增加权限变化和双重完成权；不能只删一个危险参数便宣称已完成安全整合。

BMAD Build Auto 的 `customize.toml` 已有 `implementation_handoff`、`review_layers` 接缝，可优先研究在不 fork 全仓的情况下替换执行 recipe。选择性采用时仍须审计传递引用、默认提交/撤销动作及其依赖，不是孤立复制两个段落就结束。

## 3. 框架取舍：保留什么，谁拥有最终职责

以下是建议，不是已接入能力。上游版本锁定、许可证与所选文件依赖必须随适配登记；当前临时目录不是发布依赖。

当前接入状态单独说明：Superpowers 已作为外部工程技能按需使用；cc-sdd 只有实验资源与一次 review 清单消费；Spec Kit 有实验 custom-step 接入；本表所提完整 SDD/宪法/团队集成尚未交付。其余是研究参考，不是已安装的生产流程。[既有接入证据](../2026-09-10-plugin-retrospective/README.md)

| 上游 | 拟复用的具体能力 | 在统一流程中的职责 | 不原样接入的部分 |
|---|---|---|---|
| BMAD | hub 生命周期、build-auto 的输入输出/Code Map/验证缺口与审查分类、correct-course、角色配置 | 阶段组织、工程判断与变更回退 | 常驻全员 Party、静默模拟、自动 Git 动作、第二个 sprint 完成状态 |
| cc-sdd | steering、discovery、requirements、design、tasks、跨 Spec batch review、impl/review 协议 | 需求到设计/任务的连续 SDD、边界收敛和任务执行方法 | `-y` 全量自动批准、上游硬编码模型、把 approval 布尔值视为版本绑定 |
| Spec Kit | constitution、clarify/analyze、converge；runtime 模板解析 | 长期治理原则、工件一致性、实现与已批准意图对照 | 另一套规格真源和 workflow run owner；自动替换既有工件体系 |
| Superpowers | TDD、根因调试、窄任务 brief、任务审查/定向复审、最终整体验证 | 按需工程方法，不做上层总控 | 每次重新启动完整访谈、固定重复回合、第二账本、默认提交/清理与越权裁决 |
| OpenSpec | 变更/主规格分离、结构与 delta 校验、archive 事务保护 | 作为工件更新机制的参考或独立适配候选 | 把工件存在/checkbox/archive 当代码语义通过 |
| ECC | 实际执行器中的 status/handoff、组件与安装所有权组织 | 运维/交接机制参考，领域工具按需选择 | tmux/worktree swarm、yolo profile、强制清理默认值 |
| GSD 固定旧快照 | 工件交接、恢复前交叉核验、防重复派发 | 中断恢复反例与测试设计 | 自动 reset/commit/清理及未经验证的宿主隔离假设 |
| speckit-superpowers-bridge | 明确设计所有者与执行所有者、handoff/guard、避免重复规划 | 组合已有框架的直接参照 | 单 repo handoff 的第二完成权，告警后仍可写 complete 的默认语义 |
| BMAD Loop | restart 前重新核对归属、基线和进程，故障处理 | 恢复测试及运行器设计参考 | 当前阶段不作为第二引擎安装运行 |

GSD 的旧仓在当前公开页面显示已归档；`get-shit-done` 指向 `open-gsd/gsd-core`，而 `gsd-2` 指向 `open-gsd/gsd-pi`，是两条不同迁移链。本地固定快照仍可用于历史审计，不能直接当作活跃新依赖推荐。新地址仅补查了 README/manifest，没有进行同等深度的现行运行审计。[Core 迁移公告](https://github.com/gsd-build/get-shit-done)、[Pi 迁移公告](https://github.com/gsd-build/gsd-2)

“直接复用”的交付证据应包含：上游文件/SHA → 适配差异 → 实际阶段消费记录 → 产物 → 行为验收。只有理念相似、模板落盘或文档有名称，只能分别称“借鉴”“已打包”，不能称“已接通”。

## 4. 社区经验与反证

社区原始报告属于 Tier 4 使用信号；即使有复现步骤，也不等于我们复现过，更不代表发生率。Issue 关闭与关联修复单独记录。完整作者、日期与链接见 sources.md。

### 4.1 流程完整，也可能失去收敛

Superpowers #2112 报告固定任务在复审中不断加入新加固项，真实运行验证迟迟无法开始；原文现在显示 Closed，搜索摘要却仍显示 Open。固定源码已经包含五轮上限、定向复审和剩余项裁决，因此不能拿旧报告断言现版仍完全没有边界。[原始报告](https://github.com/obra/superpowers/issues/2112)

另一个用户 #1120 记录机械任务反复冷启动和两段审查的额外开销；这是独立用户的类似痛点，不是定量效益基准。[原始报告](https://github.com/obra/superpowers/issues/1120)

**对我们的要求：**测试和审查可以发现新缺陷；不能因为没写进最初测试就忽略真实漏洞。必须区分已有约束的缺陷、规格矛盾、新需求、建议加固和误报。相关高风险问题阻断或升级决定；无关加固记入后续，不无限吸入本次。达到修复预算不等于自动验收，也不能降低标准。

### 4.2 “装了技能”不等于接通宿主

Superpowers #647 曾报告 Codex 技能要求的 Task/named reviewer 路由没有随技能安装接通；已关闭并关联适配修复。这是历史接缝缺陷，不是今天 Codex 没有子代理的证据。[原始报告](https://github.com/obra/superpowers/issues/647)

BMAD Loop #471 记录 Codex worktree/hooks 交接超时；当前固定源码已在默认 `seed_adapter_defaults` 路径补 hooks config 播种，原问题已关闭。应吸收它的验收教训，不能称现版仍未修。[原始报告](https://github.com/bmad-code-org/bmad-loop/issues/471)

**对我们的要求：**从安装后的唯一入口实测角色派发、代码候选、审查交接、失败与恢复，而不是只测源代码 CLI、manifest 或根目录 preflight。所需本地 runtime 必须随产品有明确路径和版本，不能依赖研究目录。

### 4.3 “完成记录”不等于真实完成

BMAD Loop #299 记录 commit 已写 DONE、目标分支尚未集成之间的崩溃窗口；这轮未复跑该问题或证明固定版本仍受影响。它与我们的到期待审失败不是同一个 Bug，但都提示必须区分工作完成、结果被接受和目标环境可见。[原始报告](https://github.com/bmad-code-org/bmad-loop/issues/299)

**对我们的要求：**每个故障拒绝条件都要有安全后继或明确阻碍；保留候选、绑定版本、拒绝旧代次，但不能永远卡在 review-required。不得通过改历史回执、删测试或简单延长超时制造通过。

### 4.4 抽象隔离与真正隔离不是一回事

GSD #3360 曾报告 Codex 原生编辑并没有随 shell 的 cd 切到 worktree；问题已关闭，固定流程对相应组合选择拒绝运行。它不证明所有现版 Codex 都无隔离能力，只证明“写一句在另一个目录工作”不等于隔离已成立。[原始报告](https://github.com/gsd-build/get-shit-done/issues/3360)

**对我们的要求：**首版共享代码树只设一个写入者；读研究可并行，依赖/同文件修改串行。验收期间冻结候选，检查前后树身份；声明 allowed paths 只是接受结果时的校验，不是同权限进程的文件系统沙箱。

### 4.5 文档自身也会积累债务

Spec Kit 用户曾报告升级覆盖 constitution 的问题；当前固定源码/变更记录已有保留与 runtime template resolution 的改动。因此长久治理资产和供应商模板必须分离。[历史讨论](https://github.com/github/spec-kit/discussions/1278)、[模板传播调整](https://github.com/github/spec-kit/pull/3790)

cc-sdd #91 的多仓使用者需要稳定 ID、owner、hash 与 CI 关联，不能依赖未知字段“碰巧没被覆盖”。此请求未成为已证实的完整跨仓能力。[原始报告](https://github.com/gotalab/cc-sdd/issues/91)

**对我们的要求：**规范、角色、工件的职责必须显式；升级保留用户写入，生成/缓存文件可再生，审批和验收绑定具体修订。不能只改文件哈希，把过期的语义决定继续标作有效。

### 4.6 工程团队的正面经验与适用边界

Anthropic 在长任务应用实验中分离 planner/generator/evaluator，并让 evaluator 操作真实应用；后来逐项消融部分流程，而非一次删光。其结果是特定任务与模型的工程经验，不证明完整流程或独立审查在所有任务都能去除。[工程实践](https://www.anthropic.com/engineering/harness-design-long-running-apps)

Cursor 的一月实验从平等抢任务转向分工；七月进一步记录重复架构决策、文档分歧和多视角审查。其吞吐导向、允许破坏再协调等策略不能直接移植到“架构稳健优先”的个人插件。[一月实践](https://cursor.com/blog/scaling-agents)、[七月后续](https://cursor.com/blog/agent-swarm-model-economics)

**综合判断：**明确职责、可追溯工件、独立验收和持续实测比角色数量更重要。采用多代理应让观点和上下文分离；不能保证错误统计独立，更不能保证零技术债。

## 5. 推荐的完整目标范式（待确认）

```text
项目宪法 + 项目事实/记忆 + 用户目标
    ↓
需求/领域/架构/测试角色调查与对抗澄清
    ↕ 需求、Spec、设计、契约持续修订；保留理由与版本
就绪审查：可验证目标、边界、依赖、未决问题、批准范围
    ↓
任务图 → Codex 实现 → 验证 → 独立审查 → 有界修复
    ↕ 实现差距回代码/任务；意图变化回 Spec/设计审批
跨任务/跨层集成验收 → 可交付证据 → 复盘
    └→ 已核实事实进入记忆；长期规则变化走宪法修订
```

所有阶段由同一个入口推进；不是要求用户逐一输入 BMAD/kiro/speckit 命令。项目宪法不越过用户授权与平台规则。完整是职责覆盖，不是所有任务都执行相同数量的会议、文件、代理或测试。

一个 develop 路由/准入入口不等于一个新的常驻自研引擎。优先由宿主运行阶段与角色，复用固定版本的上游资源产出/校验工件，以现有 journal 接受完成结果；任何新增控制器职责须说明现有原语的具体缺口，并通过真实宿主验收。若未来更换唯一完成所有者，必须有显式迁移决定，不能让两套状态并行裁决。

### 四层职责

1. **治理与工件层**：宪法、项目记忆、Spec/设计/契约、验收、任务、决定与证据。现有规格位置继续有效，工件相互引用，不新建竞争真源。上游需要的路径通过适配视图/解析映射，不默认复制四份可编辑规格。
2. **阶段与团队层**：按阶段选角色、发出有明确输入/输出/权限的任务、收集反例、裁决回退点。团队可以调整，但批准意图与技术债原则不能静默降低。
3. **执行与状态层**：宿主真实运行代理；现有控制器能力按需演进，负责接受结果、记录依赖、失效、预算与安全恢复。讨论、模板和工具输出不能自己拥有第二套完成权。
4. **宿主与领域适配层**：Codex 首先；后续 Claude/Cursor 共享同一规格/角色/阶段语义，工具和权限接缝分别实测。全栈、训练、Agent 使用不同的行为验证，不改变统一主流程。

### 两种收敛不得混淆

- **Spec 收敛**：补全不明确目标和边界，校验需求/架构/接口/验收矛盾；依据反证修订，保留决定。批准前自动整理技术事实；批准后意图、契约或重大架构变化需明确新决定。新版本使受影响下游审批/结果待复核，不重跑未受影响工作。
- **实现收敛**：对照已批准意图，追踪 missing/partial/contradicts/unrequested；修实现或提出追加任务。不改 Spec 来把错误实现合法化。Spec Kit converge 本身只追加任务而不改 spec/plan，这一点必须保留。

当前 C2 计划不可追加、带治理 assessment 的组合计划也不支持；因此“追加收敛任务”和“治理贯穿多任务”是明确的新适配缺口，不能写进提示词后当作已经可用。

### 建议团队组织

协调/最终裁决保留在主线程；需求/产品和领域分析支撑发现；架构角色持有跨模块决策；实现者只拥有分配写入范围；测试/评测角色以行为找反例；独立审查角色检查意图、边界与证据。不同阶段可复用同一个角色，但实现者不得兼任自己的最终独立验收者。

首轮独立观点 → 指定矛盾交叉回应 → 实证检查 → 协调者裁决/用户决策。没有发现允许返回 clean；有分歧允许保留，不能为“对抗”强制找问题或为“完成”强制共识。重大安全/数据问题不能被简单归为超范围而略过，应阻断受影响动作并请求决定。

## 6. 下一步建议：按用户结果验收，不按底层模块数量汇报

本节是研究建议，不是已经批准的执行计划。下一轮若获实现授权，按现有 kickoff/规格流程只解决剩余重大决定，更新既有 spec/plan，不再重复整套需求访谈或建第二套规范系统。

| 顺序 | 可检查交付物 | 通过标准 |
|---|---|---|
| 1. 补齐目标和职责 | 既有规格的修订草案、原始需求→阶段/角色/模块/验收映射、上游采用清单 | 宪法、Spec 连续收敛、BMAD 团队/对抗、完整管线、恢复、架构债务和三类项目没有缺席；不同审批范围不混淆 |
| 2. Codex 团队接缝验证 | 一个真实安装入口可找到角色资源和运行时；团队两轮独立/交叉意见；角色丢失后可重建 | 真代理、真消费上游资源、无静默模拟、无新增安全绕过；不以改工具名代替运行验证 |
| 3. 第一条完整纵向流程 | 在一个受控小项目跑通治理→Spec→设计→任务→实现→独立审查→收敛→集成→复盘 | 注入一次规格矛盾和一次实现缺陷；正确回退；冻结用户目标；无需用户手工换插件/改内部账本 |
| 4. 恢复和漂移回归 | 修复现有到期待审/Node 路径接缝；追加任务与依赖失效；重启/迟到结果/冲突检查 | 不伪造历史、不重复未知副作用、旧候选不被误接受、后续任务合法解锁；原有脏文件保留 |
| 5. 场景化与分发验收 | 全栈、训练、Agent 各自案例；同输入基线对比；可安装版本与来源锁 | 每项分别报告通过/失败/未运行；Codex 可用不冒称三端可用；GitHub 发布另行获授权 |

步骤 2–4 构成首个**核心编排验收包**，不能据此宣称统一工具已经适用于全栈、训练、Agent 三类项目。相应领域的 ready 要有步骤 5 的实际案例；完整版本要求所有已承诺领域与宿主均有对应证据，或由用户明确批准范围调整并保留未交付标记。有依赖的恢复修复可提前穿插，不能先宣称“团队模式完成”再无限延期真实交付。优先继续现有控制器可复用部分；若接口试验表明它不适合完整语义，再出有证据的替换决策和迁移方案，不因既有投入硬保留，也不无依据重写。

### 不再遗漏的验收条目

| ID | 用户需求 | 必须能够观察的行为 |
|---|---|---|
| R1 | 一个长期入口 | 只调用 develop 即加载正确版本并推进；不要求用户安装/切换各上游总控 |
| R2 | 宪法 | 发现具体冲突能拒绝受影响步骤；显式修订保留历史并触发相关复核 |
| R3 | Spec 持续收敛 | 需求/设计反例触发修订；实现错误不反向篡改目标；跨 Spec 接口变更使相关验证失效 |
| R4 | BMAD 团队 | 有真实角色、线程、owner、交叉意见和证据；模拟模式不能充当独立团队 |
| R5 | 完整流水线与大任务 | 依赖就绪派发、审查拒绝后修复、一次授权范围内连续推进、中断后续接 |
| R6 | Linux 式工程判断 | 对“必须重写”要求复现/调用链/局部方案对照；不把最短补丁等同最好架构 |
| R7 | 相关技术债 | 解释新变更会如何加剧风险；必要局部修复或升级决策，禁止全仓无限清理 |
| R8 | 全栈 | 真实跨层契约、数据库行为/事务与关键用户路径；不只 TS 类型或页面截图 |
| R9 | 算法训练 | 数据划分/泄漏检查、固定基线、实验配置/种子、指标来源、复现与 checkpoint 续训；算力/数据不足明确未测 |
| R10 | Agent 开发 | 工具权限与副作用、失败轨迹、检索/路由评测、固定样本与阈值；实现者不兼最终 evaluator |
| R11 | 自己 GitHub、多宿主 | 同源资源、来源/适配差异、升级保留用户资产；Codex/Claude/Cursor 各自行为验收 |

建议先冻结可复现缺陷样本与验收，再比较旧 develop 与整合版。指标包含漏掉的有效缺陷、误报和过度修复、破坏的契约、人工救援、重复执行及实际工具/时延/成本（可得时）。不宣称单个通过样例证明普遍降低错误；不按测试数量或生成行数评定质量。

## 7. 如何防止再次发生同类偏移

1. **需求覆盖是每阶段的输入，不是总结时补写的表。**若 R2/R3/R4 等目标尚无实现/证据就明确列缺口，不把其他成功抵消。
2. **每个自研组件说明为什么上游不能满足。**列出具体接缝与行为验收；没有增益证据的包装层不持续扩张。
3. **架构改变要显式留痕。**采用/替换上游、削减生命周期、增加状态所有者或权限，列出对原目标的影响并取得决定；不得借“轻量化”静默删需求。
4. **同时测试安全拒绝和可继续性。**每个持久交接验证“拒绝错结果”与“可在有效证据下前进”，恢复不能只是存在一个命令。
5. **进度以可见能力开头。**分开源码实现、打包、宿主加载、真实使用与完整版本；未测、失败、受限不能写成“基本完成”。
6. **流程本身做消融。**有益的独立验收保留；重复访谈、重复账本、纯仪式性代理回合要用证据精简。不能预设越重越稳或越轻越现代。

这套机制降低再次偏移的风险，不是保证模型以后绝不犯错；它让偏移更早暴露、能被具体指出并纠正。
